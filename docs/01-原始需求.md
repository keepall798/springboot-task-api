# 01 · 原始需求

> 记录起点：我最开始到底要做什么。需求写得越清楚，后面越少返工。

## 1. 一句话需求

用 Java 实现一个**任务清单的增删改查后端接口**，只做接口，不做前端。

## 2. 明确的约束条件

| 约束 | 具体要求 | 我的处理 |
|---|---|---|
| 语言 | Java | 使用 Java 17 语法，JDK 17+ 均可运行 |
| 后端框架 | Spring Boot + JPA 或 MyBatis | 选 Spring Boot 3.5.16 + Spring Data JPA |
| 数据库 | MySQL 或 PostgreSQL | 选 MySQL（本机已装 5.7.29） |
| 数据表 | 一张 `task` 表 | 字段：主键、标题、状态、创建时间 |
| 接口数量 | 5 个 REST 接口 | 新增、查全部、查单个、更新、删除 |
| 配置 | 数据库配置写在配置文件 | 放 `application.yml`，Java 代码零硬编码 |
| 交付物 | 源码、SQL、配置、README、测试记录 | 全部放进本仓库 |

## 3. 功能边界（做什么 / 不做什么）

### 要做

- 任务的**新增**：标题必填，状态可选
- 任务的**查询**：全部列表 + 按 id 查单个
- 任务的**更新**：改标题、改状态
- 任务的**删除**：按 id 删除
- 参数校验：标题不能为空、不能超长；状态只能是固定几种
- 统一的错误返回：找不到返回 404，参数错返回 400
- 可运行的数据库脚本、配置文件、说明文档
- 接口测试记录（证明真的能跑）

### 不做（明确排除，避免范围膨胀）

- ❌ 前端页面
- ❌ 用户注册 / 登录 / 权限
- ❌ 任务分类、标签、附件、提醒
- ❌ 分页、搜索、排序接口（作为后续练习）
- ❌ 多租户、软删除、审计日志

## 4. 为什么这样定边界

我是来学**后端 CRUD 的完整链路**的：从 HTTP 请求进来，到数据库落库，再到 JSON 返回。

如果一开始就加登录、加前端、加分页，注意力会被分散到「怎么配 Spring Security」「怎么写 Vue」，而不是「一个接口是怎么从 Controller 走到 SQL 的」。

所以第一版刻意做小：**5 个接口，一张表，把每一层都写清楚**。功能扩展留到学完之后（见 [07-学习总结](07-学习总结.md) 的下一步计划）。

## 5. 验收标准（我自己定的）

满足以下全部条件才算完成：

1. `mvnw spring-boot:run` 能启动，控制台打印 `Started TaskManagerApplication`
2. `GET /api/tasks` 返回 `200` 和 JSON 数组
3. 5 个接口在 Postman 里逐个调用成功
4. 传入空标题返回 `400`，查询不存在的 id 返回 `404`
5. 数据库里能查到真实数据（不是内存假数据）
6. 把项目拷到另一台装好 JDK/MySQL 的机器上，改配置就能跑

实际验收结果：1～6 全部满足，测试记录见 [api-test-record.md](api-test-record.md)。

## 6. 需求里一个容易忽略的点

「数据库配置写在配置文件里，不要硬编码」——这句话不只是「别把密码写死在 Java 里」，还包括：

- 地址、端口、库名、账号、密码都应该可配置
- 换环境（本地 / 测试 / 生产）时只改配置，不改代码

所以最终写法是：

```yaml
url: "${DB_URL:jdbc:mysql://localhost:3306/task_manager?...}"
username: "${DB_USERNAME:task_app}"
password: "${DB_PASSWORD:TaskApp@123456}"
```

优先读环境变量，没有才用默认值。这样本地零配置能跑，部署时用环境变量覆盖密码。
