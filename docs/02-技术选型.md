# 02 · 技术选型

> 记录我为什么选这套技术，以及当时否掉了哪些方案。

## 1. 最终选择

| 层 | 选择 | 版本 |
|---|---|---|
| 语言 | Java | 17+ |
| Web 框架 | Spring Boot | 3.5.16 |
| 持久层 | Spring Data JPA（Hibernate） | 6.6.53 |
| 数据库 | MySQL | 5.7.29 |
| 连接池 | HikariCP（Spring Boot 默认） | 随 Boot |
| 参数校验 | Jakarta Bean Validation | 随 Boot |
| 构建 | Maven Wrapper | 3.9.11 |
| 测试 | Postman / Newman | 6.2.3 |

## 2. 逐项说明：为什么是它

### 2.1 为什么用 Spring Boot，而不是原生 Spring

原生 Spring 要自己配 `DispatcherServlet`、`web.xml`、Jackson、数据源……一个 Hello World 就要几十行 XML。

Spring Boot 的价值是**自动配置**：加一个 `spring-boot-starter-web`，Tomcat 和 Spring MVC 就绪；加 `spring-boot-starter-data-jpa`，数据源和事务就绪。

对学习 CRUD 的人来说，能把精力放在「接口怎么写」而不是「容器怎么配」，这是关键。

### 2.2 JPA 还是 MyBatis

| 维度 | Spring Data JPA | MyBatis |
|---|---|---|
| SQL 写法 | 基本不写，方法名推导 | 手写 SQL / XML |
| 上手速度 | 快，`JpaRepository` 直接有 CRUD | 需要先写 mapper |
| SQL 掌控力 | 弱一些（可 `@Query` 补） | 强，完全可控 |
| 适合场景 | 标准 CRUD、领域模型清晰 | 复杂查询、遗留库、SQL 优化要求高 |

选 JPA 的理由：这个项目的操作全是标准 CRUD，用 `JpaRepository` 继承一下就得到 `save / findAll / findById / deleteById`，**最适合理解「ORM 在做什么」**。

如果需求里出现多表关联统计、复杂动态条件，我会换 MyBatis 或 JPA + 原生 SQL。

### 2.3 MySQL 还是 PostgreSQL

| 维度 | MySQL | PostgreSQL |
|---|---|---|
| 本机现状 | 已装 5.7.29，直接用 | 需要新装 |
| 生态普及度 | 极高，教程最多 | 高，但相对少 |
| 特性 | 够用 | 类型系统、JSON、窗口函数更强 |

选 MySQL 的原因很朴素：**本机已经有，且教程最多**。PostgreSQL 也很好，后续可以把这个项目迁移一遍作为练习（见 07 的下一步）。

> 注意：MySQL 5.7 已经较老。Hibernate 6.6 启动时会警告「5.7 不再受支持」。实测 5 个接口都正常，但正式项目建议 MySQL 8.0+。

### 2.4 为什么用 Maven Wrapper

不装 Maven 也能构建：

```bash
./mvnw clean package      # macOS / Linux
.\mvnw.cmd clean package  # Windows
```

Wrapper 会按 `.mvn/wrapper/maven-wrapper.properties` 自动下载指定版本，**换电脑不用重新装 Maven，版本也一致**。

### 2.5 为什么接口测试用 Postman + Newman

- Postman 图形化：适合手工点、看响应、截图留证
- Newman：Postman 集合的命令行运行器，能自动化跑、能出 HTML 报告
- 测试集合本身是 **JSON 文件**，可以进 Git，别人 clone 下来导入就能复现

这比「截图证明我测过」更可信：**测试脚本本身可复现**。

## 3. 分层设计

```text
HTTP 请求
   │
   ▼
Controller    只负责：接请求、校验、返回状态码
   │
   ▼
Service       业务规则：默认状态、找不到抛异常、事务
   │
   ▼
Repository    数据访问：JpaRepository 自动实现
   │
   ▼
Entity / DTO  数据库映射 / 对外契约
   │
   ▼
MySQL
```

### 为什么要 DTO，不直接返回 Entity

1. **安全**：直接返回实体，以后加密码字段就会泄露
2. **稳定**：接口字段不随数据库表结构变化
3. **校验**：`TaskCreateRequest` 上加 `@NotBlank`，实体上不需要

### 为什么异常要统一处理

如果每个 Controller 都写 `try-catch`，代码会重复且风格不一。用 `@RestControllerAdvice` 统一转成：

```json
{
  "status": 404,
  "error": "Not Found",
  "message": "任务不存在，id=1",
  "path": "/api/tasks/1",
  "timestamp": "2026-10-20 15:23:41"
}
```

前端只需处理一种错误结构。

## 4. 被否掉的方案

| 方案 | 放弃原因 |
|---|---|
| Servlet + JDBC 手写 | 学习价值有，但重复代码太多，偏离「REST 接口」主题 |
| Spring Boot + MyBatis-Plus | 方便，但隐藏了 SQL 细节，学习阶段不选 |
| 内存数据库 H2 | 免装数据库，但学不到建表、字符集、时区这些真实问题 |
| 直接把 Entity 返回前端 | 短期省事，长期是坑 |
| 用 Lombok 简化代码 | 初学者容易「看不到 getter/setter 就懵」，本项目故意手写 |

## 5. 一句话总结选型

> **用最主流、最少配置的组合（Spring Boot + JPA + MySQL），把注意力集中在「请求怎么进、SQL 怎么出」上。**
