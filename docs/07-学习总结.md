# 07 · 学习总结与思考

> 项目写完了，真正值钱的是这一篇：哪些是「以为会了」，哪些是「真会了」。

## 1. 一个月前我以为的后端

「后端不就是写个接口，查数据库返回 JSON 吗？」

做完这个项目才发现，一个 `POST /api/tasks` 背后至少涉及：

```text
HTTP 方法/状态码/请求头
  → Spring MVC 路由与参数绑定
  → Bean Validation 校验
  → DTO 与 Entity 的边界
  → Service 事务
  → JPA 实体映射与 SQL 生成
  → 数据库字符集、时区、索引
  → 统一异常与错误码
  → 接口测试与可复现的证据
```

任何一层没想清楚，都会以「莫名其妙 400 / 500 / 乱码 / 连不上」的形式冒出来。

## 2. 五个真正学会的点

### 2.1 REST 不是「URL + 动词」

一开始我想写 `/api/addTask`、`/api/getTaskList`。后来明白：

- **资源用名词**：`/api/tasks`
- **动作靠 HTTP 方法表达**：POST 增、GET 查、PUT 改、DELETE 删
- **状态码要准确**：创建成功 `201`，删除成功 `204`，找不到 `404`，参数错 `400`

状态码不只是「好看」，它是前后端、网关、监控共同依赖的契约。

### 2.2 JPA 省的是「样板代码」，不是「理解」

`TaskRepository extends JpaRepository<Task, Long>` 一行就有了 CRUD，很爽。

但我也刻意去看了它生成的 SQL（`show-sql: true`）：

```sql
select t1_0.id, t1_0.created_at, t1_0.status, t1_0.title
from task t1_0
order by t1_0.created_at desc, t1_0.id desc
```

**结论**：JPA 让我不用手写 SQL，但索引、排序、N+1 这些问题一个都没消失，只是被藏起来了。用 ORM 更要会看 SQL。

### 2.3 枚举用 `EnumType.STRING`，别用默认

默认的 `ORDINAL` 存 `0/1/2`。我在枚举中间插一个值，历史数据就全错位了。这个坑不响，但很致命。

同样，「状态用字符串还是数字」本质是**可读性与存储效率的权衡**，没有标准答案，要看场景。

### 2.4 异常要统一，不要每个接口 try-catch

最初我在每个方法里写 `if (task == null) return 404`，代码又长又乱。

改成：

- Service 里抛 `TaskNotFoundException`
- `@RestControllerAdvice` 统一转成 JSON

前端只需要认一种错误结构。这是我第一次真切体会到「横切关注点」是什么意思。

### 2.5 测试要能复现，截图不算证据

「我测过了」没有说服力。可复现的是：

- Postman 集合（JSON 文件，能进 Git）
- Newman 命令行跑出来的报告
- 冒烟脚本 + 结果 JSON

别人 clone 下来，一条命令就能验证。**能被别人复现的测试，才是测试。**

## 3. 踩坑清单（细节见 06）

| 坑 | 一句话教训 |
|---|---|
| 8080 被占 | 关窗口 ≠ 进程退出，用 `Ctrl + C` |
| PowerShell curl 传 JSON 失败 | 别名不是真 curl，用 `curl.exe` 或 `Invoke-RestMethod` |
| 控制台中文乱码 | 先用 `HEX()` 确认数据对不对，再怀疑显示 |
| MySQL 5.7 警告 | `WARN` 不等于失败，学会读日志 |
| localhost 连不上 | 可能是 IPv6，用 `127.0.0.1` |
| 网页工具跨域 | CORS 是浏览器限制，不是接口坏 |
| root 密码未知 | 建专用账号，最小权限 |

## 4. 我还没搞懂 / 做得不够好的地方

诚实记录，避免自我感觉良好：

1. **没有写单元测试**：现在只有接口级测试，Service 的分支逻辑还没覆盖。下一步补 JUnit + Mockito。
2. **没有分页**：数据一多，`findAll` 就是灾难。`Pageable` 还没用过。
3. **没有接口文档自动化**：现在是手写 Markdown，应该用 springdoc-openapi 生成 Swagger。
4. **没有 Docker**：环境依赖还是「装 JDK、装 MySQL」，没做到一键起。
5. **没有真实服务器部署**：06 的部署流程还没实测，等有云服务器要补上。
6. **异常处理还不够细**：并发修改、唯一约束冲突这些场景没处理。
7. **日志不规范**：只用了默认日志，没做结构化、没加 traceId。

## 5. 下一步计划

按优先级：

1. **补单元测试**：Service 层用 Mockito，Controller 层用 `@WebMvcTest`
2. **加分页 + 按状态筛选**：`GET /api/tasks?page=0&size=10&status=TODO`
3. **接 Swagger**：springdoc-openapi，让接口文档自动生成
4. **Docker Compose**：MySQL + 应用一键起，彻底解决「换电脑跑不起来」
5. **真实部署一次**：买台最低配云服务器，把 06 的流程走通并补全踩坑
6. **换个数据库试试**：把 MySQL 换成 PostgreSQL，体会方言差异

## 6. 对「用 AI 辅助学习」的一点反思

这个项目是在 AI 辅助下完成的。我的体会是：

- **AI 能把代码写出来，但「为什么这么写」要自己追问**
- 每次它给出方案，我都要求它解释：为什么用 DTO、为什么 `ddl-auto: none`、为什么加索引
- 报错时不要只贴错误让它修，先自己读一遍日志，判断是配置、网络还是代码问题
- **能复述出来、能改出来，才算学会**

如果只是复制粘贴，项目能跑，但下一次换个需求还是不会。所以这个仓库重点记录的是**决策和踩坑**，不是代码本身。

## 7. 一句话总结

> 后端入门不是「会写 5 个接口」，而是**知道这 5 个接口在每一层发生了什么、坏了怎么查**。
>
> 这个项目让我第一次把「请求 → 校验 → 事务 → SQL → 响应 → 测试」串成了一条完整的线。
