# 03 · 数据库设计、建表 SQL

> 一张表、四个字段看起来简单，但字符集、时区、索引、枚举存法这些细节，才是真正会踩坑的地方。

## 1. 表结构总览

表名：`task`

| 字段 | 类型 | 允许空 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT` | 否 | 自增 | 主键 |
| `title` | `VARCHAR(200)` | 否 | 无 | 任务标题 |
| `status` | `VARCHAR(20)` | 否 | `'TODO'` | 状态：TODO / IN_PROGRESS / DONE |
| `created_at` | `DATETIME(6)` | 否 | `CURRENT_TIMESTAMP(6)` | 创建时间 |

索引：

| 索引名 | 字段 | 用途 |
|---|---|---|
| `PRIMARY` | `id` | 主键查询 |
| `idx_task_status` | `status` | 以后按状态筛选会用 |
| `idx_task_created_at` | `created_at` | 列表按创建时间倒序 |

## 2. 建表 SQL

完整脚本在 [`sql/02_create_table.sql`](../sql/02_create_table.sql)：

```sql
USE task_manager;

CREATE TABLE IF NOT EXISTS task (
    id         BIGINT       NOT NULL AUTO_INCREMENT COMMENT '任务 ID，主键',
    title      VARCHAR(200) NOT NULL                COMMENT '任务标题',
    status     VARCHAR(20)  NOT NULL DEFAULT 'TODO' COMMENT '状态：TODO=待办，IN_PROGRESS=进行中，DONE=已完成',
    created_at DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6) COMMENT '创建时间',
    PRIMARY KEY (id),
    KEY idx_task_status (status),
    KEY idx_task_created_at (created_at)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_unicode_ci
  COMMENT = '任务表';
```

建库和建账号的脚本在 [`sql/01_create_database.sql`](../sql/01_create_database.sql)。

## 3. 每个设计决定的理由

### 3.1 主键为什么用 BIGINT 自增

- `BIGINT` 上限远大于 `INT`，业务表习惯用它，避免几年后 id 不够用
- 自增主键写入快、索引局部性好
- 另一种做法是 UUID：分布式友好，但占空间、索引不连续，学习项目不需要

### 3.2 状态为什么存字符串，不存数字

两种常见做法：

| 做法 | 存什么 | 优点 | 缺点 |
|---|---|---|---|
| 数字 | 0 / 1 / 2 | 省空间、查询快 | 直接看库看不出含义，要对照文档 |
| 字符串 | `TODO` / `IN_PROGRESS` / `DONE` | 一眼看懂，调试方便 | 占一点空间 |

学习项目选了字符串：

```java
@Enumerated(EnumType.STRING)
private TaskStatus status;
```

`EnumType.STRING` 是关键。如果写成默认的 `ORDINAL`，数据库会存 `0/1/2`，**以后在枚举中间插一个值，历史数据全错位**——这是很经典的坑。

> 正式项目如果状态值极多、追求存储效率，可以考虑用 `TINYINT` + 字典表，但要配套文档和校验。

### 3.3 创建时间为什么是 DATETIME(6)

- `DATETIME(6)` 精确到微秒，同一秒内创建多条也能稳定排序
- 不用 `TIMESTAMP`：它的范围只到 2038 年，而且受会话时区影响
- 默认值 `CURRENT_TIMESTAMP(6)`：即使直接写 SQL 插入，也能自动填时间

Java 侧对应 `LocalDateTime`，并在实体里用 `@PrePersist` 兜底：

```java
@PrePersist
protected void onCreate() {
    if (createdAt == null) {
        createdAt = LocalDateTime.now();
    }
    if (status == null) {
        status = TaskStatus.TODO;
    }
}
```

### 3.4 为什么用 utf8mb4

`utf8` 在 MySQL 里最多 3 字节，存不了 emoji 和部分生僻字。`utf8mb4` 才是真正的 UTF-8。

所以库、表、连接串三处都要对齐：

- 建库：`DEFAULT CHARACTER SET utf8mb4`
- 建表：`DEFAULT CHARSET = utf8mb4`
- 连接串：`characterEncoding=utf8`

### 3.5 为什么建了索引

现在数据量小，索引感觉没用。但列表接口的 SQL 是：

```sql
SELECT ... FROM task ORDER BY created_at DESC, id DESC
```

没有 `idx_task_created_at` 就要全表扫描 + 文件排序。`status` 索引是为后续「按状态筛选」预留的。

> 索引不是越多越好：每个索引都会拖慢写入。学习阶段先建最常用的两个。

## 4. 实体类是怎么映射的

```java
@Entity
@Table(name = "task")
public class Task {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "title", nullable = false, length = 200)
    private String title;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false, length = 20)
    private TaskStatus status;

    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;
}
```

对应关系：

| 注解 | 作用 |
|---|---|
| `@Entity` | 这是一个 JPA 实体 |
| `@Table(name = "task")` | 映射到 `task` 表 |
| `@Id` + `@GeneratedValue(IDENTITY)` | 主键，交给数据库自增 |
| `@Column(name=..., length=...)` | 列名、长度 |
| `@Enumerated(STRING)` | 枚举存名字而不是序号 |
| `updatable = false` | 创建时间写入后不允许 UPDATE |

## 6. 建表时踩到的点

1. **表由 SQL 脚本创建，不让 Hibernate 自动建表**
   `application.yml` 里设置 `ddl-auto: none`。否则 Hibernate 可能按实体推断出不同的列类型，导致「代码能跑、数据库结构却和脚本不一致」。

2. **MySQL 5.7 的 datetime 精度**
   不写 `(6)` 只能到秒。同秒创建多条时排序不稳定，加上微秒后 `ORDER BY created_at DESC` 才可靠。

3. **建表脚本要可重复执行**
   用了 `CREATE TABLE IF NOT EXISTS`，重跑不会报错。
